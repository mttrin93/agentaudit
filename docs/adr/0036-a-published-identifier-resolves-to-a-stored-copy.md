# A published identifier resolves to a stored copy, or it is not a claim this repository can make

[ADR-0002](./0002-owasp-ids-as-secondary-labels.md) gives every family an OWASP identifier as a secondary label, and every case record carries the identifier it *tests one case within*. Two lists supply those identifiers: OWASP's agentic list, and OWASP's GenAI LLM list. Only the first was stored. `published.py` held a transcribed copy of `ASI01`–`ASI10` and derived the per-report coverage claim by subtracting from it; the `LLM0x:2026` identifiers on twelve of the eighteen case records had no copy at all, so what they claimed rested on whatever the author remembered at the moment of typing.

That is not a tidiness problem, and #44 is the demonstration. #42 selected `LLM06` for scope creep, no identifier for wrongful commitment and `LLM07` for data leakage. PLAN §4 carries `LLM03:2026`, `LLM07:2026` and `LLM02:2026`/`LLM08:2026` for the same three families, and the case records on disk carry PLAN §4's numbers. **Three disagreements, in a signed document's central column, and nothing in the repository could say which side was right** — because saying so requires reading the titles off the list, and the list was not there.

The failure mode this closes is worth naming precisely. A wrong identifier is not a wrong number: it is a *true-looking* claim about an external standard, printed beside a rate, in a document whose whole purpose is that a reader who has never used the bench can check it. `LLM07:2026` on a wrongful-commitment record is Misinformation and is defensible; the same string under the 2025 edition is System Prompt Leakage and is nonsense. Nothing in the string says which, and nothing downstream can tell.

## Decision

1. **Both published lists are stored, in `editions.py`, as `StoredCopy` records.** One record per edition: the edition's name, the tag it carries inside an identifier, and its entries as `PublishedCategory(identifier, title)` — identifier and title, and nothing else. Titles verbatim.
2. **Every identifier a case record claims resolves to an entry in a current stored copy, and `ExternalId` refuses one that does not.** The check is on the record's own type rather than in `load_case`, so both ways in are covered by one guard: a case the adaptive layer proposed is written into the library by the run that admitted it ([ADR-0033](./0033-an-admitted-route-is-written-into-the-library.md)), and an unresolvable identifier that reached the disk would be a record the loader refuses for ever after.
3. **`ORIGINATED_HERE` is the only claim that resolves to nothing and is still valid.** Halt defeat and disclosure denial originated in this project and claim no published identifier on either list (ADR-0002, PLAN §4). That is a declared constant, so *this case claims no published identifier* is a sentence a reader can find rather than a blank a typo can imitate.
4. **A case record's identifier names its edition, and the edition it names must be the stored one.** `LLM07:2025` does not resolve against a repository holding the 2026 copy, even though the 2026 copy carries `LLM07` — it is Misinformation there and System Prompt Leakage in 2025. This is the anti-drift device: adopting a new edition is a change every existing claim fails until someone re-reads it, rather than a copy swapped underneath identifiers nobody re-checked.
   - **The tag is required of a claim and optional in a lookup, and the asymmetry is deliberate.** `resolves("LLM06")` answers — one current copy per list carries that number, so a caller holding a copy and asking *what is `LLM06`* is asking a question with one answer, and `published.FAMILY_CATEGORY` asks exactly that with bare `ASI01`. But an untagged identifier *stored on a record* is a wildcard: `LLM06` means Excessive Agency in the numbering #42's table was written in and Unbounded Consumption in the copy stored today, and it would go on meaning whatever the current copy last said. So the tag requirement lives in `not_a_claim`, which is the whole of what `ExternalId` refuses, and the guard this decision advertises is not left with a hole in the shape of an omitted tag.
5. **The superseded edition is stored beside the current one, and licenses nothing.** `CURRENT` filters on `superseded_by`, so no identifier resolves to a superseded entry, no coverage claim can be made against one, and its only job is diagnosis: `refusal` tells a reader that `LLM06:2025` is Excessive Agency and that the current edition numbers that entry `LLM03:2026`.
6. **The renumbering between two editions is derived from the copies by title, not declared.** `renumbering` matches titles by equality, so it cannot pair two entries the copies do not agree about; an entry it cannot match is a raise rather than a missing pair. `RETITLED` declares only the pairs no title match can find — today one, `LLM07:2025 System Prompt Leakage` into `LLM08:2026 Hidden Context Exposure`.
7. **The copies live apart from the judgements about them.** `editions.py` holds copies and lookup; `published.py` holds which family claims what, why an unclaimed entry is unclaimed, and the subtraction. This is forced as well as tidy: `published.py` imports `Family` from `library.py`, so it cannot be what `library.py` imports, and point 2 requires that `library.py` can read a copy.

## What this settles, and what it deliberately does not

**Two of the three disagreements are the 2025 edition's numbering, and the lookup says so.** `LLM06:2025` is Excessive Agency, which the 2026 edition numbers `LLM03:2026` — PLAN §4's number for scope creep. `LLM07:2025` is System Prompt Leakage, which the 2026 edition carries as `LLM08:2026` Hidden Context Exposure — the second of the pair PLAN §4 carries for data leakage. So #42's table was numbering against the superseded edition, PLAN §4 and the case records were numbering against the edition its identifiers name, and **no case record's identifier changes**.

**The third is not a numbering disagreement at all, and the losing side is still stated.** #42 gave wrongful commitment no LLM identifier, so there is no number to renumber; a lookup cannot adjudicate a refusal. What it does establish is that `LLM07:2026` exists, is titled Misinformation, and is a defensible home for an output the user acts on that the operator cannot honour — which is the claim the three wrongful-commitment records already carry.

So: **`LLM07:2026` stands, and #42's *none* loses as a description of what this repository claims.** Three records claim it, nothing in this decision removes a claim, and a blank in #42's table was never going to unmake one on disk. What is genuinely open is narrower than the row suggests — whether the *family* claims Misinformation as a label, which is the label record (#45) and the identifier claims (#47), and neither is decided here. Recording the boundary that way rather than deferring the whole row is the point: a checklist item answered *by the lookup, as far as a lookup reaches* is not the same as one left for later.

**No coverage claim moves here.** The LLM list is stored and is *not* subtracted from. Deriving that list's negative coverage needs a reason beside every unclaimed entry and a per-family reading of both lists, and every one of those entries removed from an untested list is a coverage claim getting wider — the one direction nobody checks (`published.py`). This ADR gives #45 and #47 a lookup to do that against; it does not do it for them.

## What a reader sees when a copy has gone stale

Worth stating, because "prevent silent drift" is only meaningful if the loud version is described.

- **A new edition renumbers, and someone updates the copy.** Every case record claiming the old tag stops loading, with a refusal naming the entry and its new number. The library does not load until each claim has been re-read. Loud, and at the right moment.
- **A new edition renumbers and nobody notices.** The copy still names the edition it is a copy of, and `_measured.py` prints that edition beside the derived list. A reader who checks sees a report citing the 2026 edition, and can check the 2026 edition. This repository cannot detect a publication it has not been told about; what it can do is never claim to be current when it is only claiming to be a copy of a named edition, which is why `StoredCopy.edition` exists and why the fetch date is not what is stored.
- **A copy is edited to a paraphrase.** `renumbering` fails: a retitled entry that is neither a title match nor a declared rename raises, which is the shape a garbled or half-updated copy arrives in. Titles are matched by equality and never by containment — `Supply Chain` is a substring of a title two secondary readings gave the 2025 entry, and a containment match would have paired them while the publisher's own page says nothing of the kind.

## Provenance, and it is not the same for both copies

A copy is not the source, and the two copies in the tree are not equally strong. Each says so on itself rather than under one blanket sentence.

- **The LLM 2026 copy** was read on 2026-09-03 from the README of the publishing project's own repository, `GenAI-Security-Project/GenAI-LLM-Top10`, which names `2026/final/` as the canonical source, and was independently corroborated by three secondary readings that agreed with it on all ten identifiers and titles. It is still not a byte-for-byte fetch — the README was read through a page-to-text conversion — so what it claims is a faithful reading of the primary document rather than the document.
- **Two further readings disagreed** with the publisher and with each other below `LLM03`, and that is recorded on the copy. It is the fact that makes storing a copy worth the trouble: *the readings did not all agree*, so a memory of the list was never going to be safe.
- **The agentic copy** is two agreeing independent secondary readings from 2026-08-20, because the OWASP resource page refuses automated retrieval. Unchanged by this ADR, and now stated on the copy rather than in a module docstring covering both.
- **The LLM 2025 copy** was read from the publishing project's own archive page for that edition and corroborated by two independent secondary readings.

**Attribution.** Both lists are published by the OWASP GenAI Security Project under the Creative Commons Attribution-ShareAlike 4.0 International licence. What is stored is each entry's identifier and title and nothing else — no descriptive text, no mitigations — because a copy carrying the published discussion would be a redistribution this repository has no reason to make, and because the identifier and the title are the whole of what a coverage claim needs in order to be checkable.

## Considered options

- **Keep the copies as declared literals, and add a digest of them.** Rejected as adding nothing. A digest of our own transcription proves only that we did not edit our own file, which git and CI already prove; it says nothing about fidelity to the publisher, which is the only property in question. The stored copy's defence against local editing is that it is reviewed and that `renumbering` and the roster test fail on a mangled one.
- **Store only the 2026 copy, and state the resolution in prose.** The obvious smaller change, and rejected because the sentence it would leave behind — *the selection was numbering against a different edition* — is itself an unbacked claim about an external standard, printed nowhere but believed everywhere, which is the bug this ADR exists to remove. It would also give `refusal` nothing to say: a reader who wrote `LLM06:2025` would be told the number is unknown, when in fact it is a real entry at the wrong number, and those two mistakes need different fixes. The cost is honest — a second copy to keep, and a `RETITLED` pair per rename — and it buys the difference between a lookup and an opinion.
- **Store the lists as data files and load them at import.** Rejected for now. The case records are `.toml` because cases are data that is added, retired and diffed (`library.py`); a published list is neither added to nor diffed by this project, and a Python literal is read by the same reviewer who reads the code that uses it. This is a shape that can change without changing any decision above.
- **Fetch the list at run time, or in CI.** Rejected outright. A report's identifier claims would then depend on a network call, a signed document would not be reproducible, and CI would fail — or worse, pass flakily — on someone else's outage. The point of a stored copy is that the claim is checkable *offline, against something committed*.
- **Renumber the case records to #42's selection.** Rejected on the lookup: #42's numbers are the superseded edition's numbers for the same entries, so renumbering would have moved the records *away* from the edition their own tags name. #44 asked for the resolution to be a lookup rather than an opinion, and this is what the lookup said.
- **Validate identifiers in `load_case` only.** Rejected per decision 2: it leaves the write path open, and a case written with an unresolvable identifier breaks its library permanently.
- **Let a superseded identifier resolve, and warn.** Rejected. A warning in a run's output is not read by the reader of the document, and the claim would still print. The whole value of the edition tag is that it is checked, not noted.

## Consequences

- `editions.py` is a new module with no dependency on anything else in `backend/bench`, which is what lets `library.py` import it. Nothing in it decides anything about this bench.
- `published.EDITION` and `published.AgenticCategory` are gone: the edition is `AGENTIC_TOP_10_2026.edition` and the record is `editions.PublishedCategory`. `untested_categories` takes a `StoredCopy` so its raise can name which published list a claim failed against, now that there is more than one.
- **A test asserts the roster of identifiers the library claims**, so a case arriving with a fifth identifier is a decision somebody makes rather than one that lands. It resolves or the test before it fails; what the roster forces is that somebody reads the entry it resolved to.
- The bench still derives negative coverage over one list of the two, and [docs/validation.md](../validation.md) records what has and has not been checked about a stored copy.
- **A future edition of either list is a library-version event**, not a copy edit: every claim written under the old tag fails to load until it is re-read, which is by design and will feel expensive exactly once.
